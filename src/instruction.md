# Bank of Z — `src` Instructions

This folder contains all source code for the Bank of Z sample application: a static web
frontend, a z/OS Connect OpenAPI layer, and the mainframe (CICS / IMS / batch / MQ) programs
behind it.

## Folder layout

```
src/
├── frontend/   Static HTML + vanilla JS UI (Carbon Web Components). No build step.
├── api/        z/OS Connect OpenAPI project (Gradle, plugin com.ibm.zosconnect.gradle)
│   └── src/main/
│       ├── api/          openapi.yaml and API definitions
│       ├── operations/   API operation mappings
│       ├── zosAssets/    One folder per backend program (INQCUST, CREACC, XFRFUN, IBTRAN, ...)
│       ├── config/ liberty/ web.xml
└── base/       Mainframe programs
    ├── cics/   COBOL programs (CRECUST, INQACC, XFRFUN, ...), BMS maps, copybooks
    ├── ims/    DBDs, PSBs, COBOL/PL/I programs, Java, and seed data (LoadData/)
    ├── batch/  Monthly statement job (COBOL + PL/I + JCL)
    └── mq/     Java MQ components
```

## Request flow

```
Browser (src/frontend) → /api/* → z/OS Connect (src/api, port 9080/9443) → CICS / IMS programs (src/base)
```

## Running the frontend (UI only, no backend)

Requirements: Python 3 (or any static web server) and internet access (Carbon is loaded from the IBM CDN).

```bash
# from the repo root
python3 -m http.server 3001 --directory src/frontend
```

Open http://localhost:3001 (redirects to `admin.html`).

All pages render, but API calls (`/api/...`) return 404 because there is no backend or proxy
in this mode.

Stop the server: `pkill -f "http.server 3001"`.

## Running the full stack (frontend + z/OS Connect)

Requirements: Docker Desktop and credentials for a z/OS environment.

1. Create `dev/.env` with:
   ```
   CICS_USER=
   CICS_PASSWORD=
   CICS_HOST=
   CICS_PORT=
   IMS_USER=
   IMS_PASSWORD=
   IMS_HOST=
   IMS_PORT=
   IMS_DATASTORE=
   ```
2. Start it:
   ```bash
   cd dev
   docker compose up
   ```
3. Frontend: http://localhost:3001 (nginx proxies `/api/*` to z/OS Connect)
   z/OS Connect: http://localhost:9080 / https://localhost:9443

Do not run the Python server on port 3001 at the same time as the Docker stack.

## Frontend configuration

`src/frontend/config.js` picks the API base URL from the page's port:

| Frontend served on | API base URL |
|---|---|
| port 3001 | `/api` (relative, proxied by nginx) |
| any other HTTP port | `http://<host>:9080/api` |
| any other HTTPS port | `https://<host>:9444/api` |

The sort code is fixed at `987654` (`config.defaults.sortCode`).

## Using the app

- Everything starts from a customer ID entered in one lookup box.
- Prefix `C` = CICS customer (e.g. `C0000000042`), `I` = IMS customer (e.g. `I000000015`).
- IMS supports only view/update customer, list accounts, view account and credit/debit.
  Other actions show "not implemented for IMS" (guards in `frontend/js/api.js`).

## Migration dashboard

`frontend/migration-dashboard.html` (header link **Migration dashboard**) tracks the conversion
from COBOL / PL/I / JCL / CICS / IMS / DB2 to Java Spring Boot, React and PostgreSQL:
code converted %, components by status, conversion by layer and language, mainframe
dependencies replaced, test results and coverage, and mainframe vs modern performance.

It reads `frontend/data/migration-status.json`, generated by:

```bash
python3 scripts/migration-inventory.py            # re-scan src/base, keep tracked fields
python3 scripts/migration-inventory.py --sample   # fill untracked fields with sample values
```

- The legacy inventory (files, lines, `EXEC SQL`, `EXEC CICS`, DL/I calls) is always real.
- Per component, record real progress by editing `status`
  (`not-started`, `in-progress`, `converted`, `tested`, `validated`), `targetLoc`,
  `tests` (`total`, `passed`, `failed`, `coverage`) and `performance`
  (`unit`, `legacy`, `modern`). Re-running the script keeps these values.
- **COBOL source size** uses the counting method from *Mainframe COBOL Applications for
  Conversion Testing*: `.cbl`/`.cob`/`.cobol` program files, COPY not expanded; physical
  lines vs nonblank, noncomment lines, split into CICS, IMS and batch.
- **Parity test matrix** (`parity.areas`): per test area record `scenarios`
  (`total`, `executed`, `passed`, `failed`). **Execution sequence** (`parity.steps`): set each
  step's `status` to `not-started`, `in-progress` or `done`. Re-running the script keeps these.
- While `"sample": true` is set in the JSON the page shows a "Sample data" warning.
  Set it to `false` once the figures are real.
